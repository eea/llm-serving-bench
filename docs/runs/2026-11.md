# Run log — 2026-11-03 Qwen 3.8 27B on vLLM 0.32 (`results/2026-11-03_qwen3.8-27b_a`)

**Status: provisional, and not a like-for-like comparison.** n=1 per scenario, and
**this run used two GPUs where every 2026-08 run used one** (`--data-parallel-size
2`, `CUDA_VISIBLE_DEVICES=0,1`). Registered so the numbers are on the record and
auditable, not because the comparison is defensible yet.

Serve config: [`bench/serve/qwen3.8-27b.yml`](../../bench/serve/qwen3.8-27b.yml)
— supplied by the operator after import; the run itself recorded nothing.

## Headline — aggregate vs per GPU

| Metric | 2026-08-04 (1 GPU) | 2026-11-03 (2 GPUs) | Δ aggregate | **Δ per GPU** |
|---|---:|---:|---:|---:|
| mean total tok/s | 5,545 | **8,329** | **+50 %** | **−27 %** |
| peak total tok/s | 10,488 | **18,051** | +72 % | −14 % |
| mean `out_tok_s` | 2,240 | **3,189** | +42 % | −29 % |
| mean req/s | 4.94 | **6.92** | +40 % | −30 % |

Per-GPU total throughput by scenario:

| In \ Out | 128 | 512 | 1024 | 2045 |
|---|---:|---:|---:|---:|
| **128** | −39 % | −38 % | −34 % | −31 % |
| **512** | −30 % | −33 % | −32 % | −29 % |
| **1024** | −20 % | −28 % | −31 % | −26 % |
| **2048** | −14 % | −11 % | −16 % | −16 % |

**So: as deployed, the service got ~50 % faster and TTFT halved. Per GPU it got
~27 % slower.** The win is bought with a second GPU, and the efficiency of that
second GPU is poor — DP=2 should be close to neutral per GPU, not −27 %.

## Decomposition

**Prefill: ~1.9× aggregate, which is roughly what DP=2 alone predicts.** TTFT
slope 4.11 → ~1.6–2.2 ms per input token, aggregate prefill ~12k → ~23–31k
tok/s. With 100 requests split across two engines, each engine prefills about
half of them, so halving TTFT and doubling prefill throughput is the expected
DP result. **There is no evidence in this dataset of an engine-level prefill
improvement.** Reported `queue_times` are tiny (mean ~10 ms, max 23 ms).

**Decode: speculative decoding plus lower per-rank load.** In all 16 files
`median_ITL / TPOT == spec_accept_len` exactly:

| scenario | median ITL (per step) | acceptance length | TPOT (per accepted token) |
|---|---|---:|---|
| in128/out2045 | 32.7 → 44.0 ms (**+34 %**) | 3.03 | 32.6 → 13.4 ms (−59 %) |
| in1024/out1024 | 33.6 → 44.9 ms (+34 %) | 2.81 | 36.7 → 16.0 ms (−56 %) |
| in2048/out2045 | 38.3 → 48.0 ms (+25 %) | 3.21 | 41.7 → 15.2 ms (−64 %) |

Each step is 25–43 % **slower**; the win is 2.2–3.2 accepted tokens per step
(MTP). Acceptance rises monotonically with output length (39–42 % at out128 →
68–74 % at out2045): the first tokens after prefill are the ones that miss.
Part of the remaining per-token gain is simply that each rank decodes far fewer
sequences than the old single GPU did.

## Concurrency: the earlier hypothesis was wrong

In-flight decode concurrency (`out_tok_s × TPOT`, Little's Law):

| | mean | range | per GPU |
|---|---:|---|---:|
| 2026-08-04 (1 GPU) | 83.5 | 56 – 99 | ~84 |
| 2026-11-03 (2 GPUs) | 55.0 | 48.8 – 58.1 | **~27** |

`--max_num_seqs 969` **rules out the sequence-count cap** suggested when this run
was first registered. The remaining candidates for ~27 resident sequences per
rank:

1. **KV residency.** `--kv-cache-dtype fp8` was dropped, so KV bytes per token
   roughly double — half as many sequences fit per rank as in 2026-08.
2. **MTP overhead.** Each resident sequence carries 3 draft-token slots plus the
   draft (MTP) weights, further shrinking the KV budget.
3. **DP load balancing** — 100 requests across 2 ranks is not necessarily even.

The definitive check is the server startup block per rank: `GPU KV cache size:
N tokens` and `Maximum concurrency for 262,144 tokens: X.Xx`. Until then the
concurrency figure is a symptom, not a diagnosis.

## Data-quality notes on these files

- `max_output_tokens_per_s` is broken (near-constant 2,150–2,350, *below* the
  average `output_throughput` in 13 of 16 files). Not ingested.
- `mean_itl_ms` is inflated by chunked-prefill stalls (p99 ≈ 660 ms at short
  outputs); `itl_median_ms` is the per-step time and is what the decomposition
  above uses.
- Acceptance rates come from a `random` dataset under greedy decoding — real
  traffic will accept less, so expect the decode gain to shrink in production.
- No `_env.txt` capture: GPU model and driver are still unrecorded (the count is
  now known from the compose file).

## What to run next, in priority order

1. **Qwen 3.8 on 0.32 on ONE GPU** (`--data-parallel-size 1`) — the only way to
   answer "is the new stack better per GPU?".
2. **Qwen 3.8 on 0.32, one GPU, spec decode off** — separates engine gain from
   MTP gain.
3. **Qwen 3.6 on 0.32, one GPU** — separates checkpoint from engine.
4. **Restore `--kv-cache-dtype fp8`** (or raise it deliberately) and re-measure;
   if per-rank concurrency rises, the −27 % per-GPU gap is largely a residency
   problem, not a model problem.
5. Re-run the winner with `bench/run.sh`, **≥3 repeats**, with `_env.txt` capture.
6. Keep `--backend` identical across runs from now on.

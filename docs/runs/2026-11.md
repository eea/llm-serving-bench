## Decomposition — where the speed actually comes from

**Prefill: ~1.9×, and it is not spec decode.**

| | intercept | slope (ms per input token) | aggregate prefill rate |
|---|---:|---:|---:|
| 2026-08-04 | ~540 ms | 4.09–4.12 | ~11–12.5k tok/s |
| 2026-11-03 | ~300–550 ms | 1.56–2.23 | ~18–31k tok/s |

Reported `queue_times` are tiny (mean ~10 ms, max 23 ms), so the old ~0.5 s fixed
component is genuinely gone rather than re-attributed.

**Decode: entirely speculative decoding.** In all 16 files
`median_ITL / TPOT == spec_accept_len` exactly:

| scenario | median ITL (per step) | acceptance length | TPOT (per accepted token) |
|---|---|---:|---|
| in128/out2045 | 32.7 → 44.0 ms (**+34 %**) | 3.03 | 32.6 → 13.4 ms (−59 %) |
| in1024/out1024 | 33.6 → 44.9 ms (+34 %) | 2.81 | 36.7 → 16.0 ms (−56 %) |
| in2048/out2045 | 38.3 → 48.0 ms (+25 %) | 3.21 | 41.7 → 15.2 ms (−64 %) |

Each step is 25–43 % **slower**; the win is 2.2–3.2 accepted tokens per step.
**With speculative decoding disabled this stack would most likely be slower per
output token than the 2026-08 run.** Acceptance also rises monotonically with
output length (39–42 % at out128 → 68–74 % at out2045): the first tokens after
prefill are the ones that miss.

## The part that did not get captured

In-flight decode concurrency (`out_tok_s × TPOT`, Little's Law):

| | mean | range |
|---|---:|---|
| 2026-08-04 | 83.5 | 56 – 99 (i.e. nearly all 100 requests generating at once) |
| 2026-11-03 | **55.0** | 48.8 – 58.1 |

A 2.4× per-token win multiplied by a 0.66× concurrency loss lands at ~1.4×.
The concurrency is **flat at 49–58 across a 16× workload range**, and at
in128/out2045 fifty-five sequences hold only ~121k KV tokens against a
262k-token context — so this looks like a scheduler cap (`max_num_seqs`, or a
speculative-decoding default), not memory pressure. Restoring the old concurrency
at the new per-token speed implies +144 % … +175 % on `out_tok_s` in the
decode-bound scenarios instead of the +38 % … +68 % measured. Treat that as an
upper bound: more concurrent sequences costs per-step efficiency and TTFT.

## Data-quality notes on these files

- `max_output_tokens_per_s` is broken (near-constant 2,150–2,350, *below* the
  average `output_throughput` in 13 of 16 files). Not ingested.
- `mean_itl_ms` is inflated by chunked-prefill stalls (p99 ≈ 660 ms at short
  outputs); `itl_median_ms` is the per-step time and is what the decomposition
  above uses.
- Acceptance rates come from a `random` dataset under greedy decoding — real
  traffic will accept less, so expect the decode gain to shrink in production.
- No `_env.txt` capture: GPU model, driver and image tag are unrecorded.
  `bench/run.sh` captures these now; this run predates using it.
